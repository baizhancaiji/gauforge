## 0. 定位

**面向 WSL2 单机的Gaussian计算化学工作台**：以「输入 → 计算」为完整闭环，
M0–M2 即构成完整产品；分析（M3）及以后均为在此之上的功能更新。

- 强大的执行任务管理器,支持可自由修改重排序的队列任务。
- 与 HyperQueue 的关系：HQ 是本项目的**执行内核而非外部依赖**——复用其队列、
  调度、事件等功能模块，弃用其 TUI，以本工作台的 WebUI 作为综合管理面板；
  `crates/` 源码可按需修改（ADR 0001），完全独立于上游仓库演进，不做外挂式补丁。
- 非目标：多用户调度、通用作业系统、集群管理——那是上游 HyperQueue 的领域。
- 终局形态之一：作为 DeepSeek DSH 的工具被自然语言调用（见 M5）。

## 1. 设计原则

1. **领域优先**：核心抽象是 Candidate / Queue / Execution / Result（见 §2.1），
   先建模再动手。
2. **不造解析轮子**：量子化学输出的解析以 [cclib](https://cclib.github.io/) 为主；
   自写解析只允许出现在 cclib 不覆盖的实时进度场景。
3. **契约先行**：先定 API 契约（OpenAPI），前端、后端、未来 DSH 插件/工具吃同一份契约，
   杜绝字段随意漂移，为DSH插件/工具留足接口。
4. **推送不轮询**：任务状态与日志用 SSE 增量推送；SSE 事件契约属 M0 契约范围，
   须另行设计定稿，不可自由发挥。
5. **里程碑可验收**：每个里程碑有明确验收标准，写不出验收标准就不开工。
6. **文件皆入库**：导入即拷贝进工作区（§2.4），编辑与执行均不触碰用户源文件；
   Web 与 DSH 的读写范围以工作区为界。
7. **前端简约**：界面秉持简约风格，信息密度与功能清晰优先，装饰性元素从简；
   六类页面的信息架构不因视觉设计膨胀（视觉基调 M0 定稿）。

## 2. 架构方向

### 2.1 领域模型与状态机

术语表（对外 API 与文档统一使用；HQ 的 job 概念只允许出现在执行适配层内部）：

| 术语 | 英文 | 定义 |
|---|---|---|
| 候选任务 | Candidate | 已导入、未入队的输入文件副本。全局唯一 id，同一文件重复导入也生成新 id。入队或直接提交即转为任务。退回候选的路径（穷举）：历史条目「退回候选」动作、删除整条队列、待执行队列整席移除（单任务席位）、自队列移除单个未执行成员、回退队列中移除 failed/skipped 成员。候选携带**来源标记**（导入 / 未运行退回 / 失败退回-附归因 / 成功退回），回退产生的候选与新鲜导入在列表中明确区分——不能不知对错就被当作新文件直接提交。删除任务实体的动作只在本列表生效（见 Task）。 |
| 任务 | Task | 候选入队或直接提交后的形态，持有输入副本与编辑权。删除队列或被单独移除时，未执行成员一律退回候选列表；已执行过的成员在被移除或队列被删除后只存在于执行历史（回退为未提交的失败队列中，已执行成员在移除前仍列为队列成员，见下「编辑与移除边界」）。任务实体**只有在候选形态可被删除**（候选列表「-」），在任何其他位置只可退回候选、不可删除。 |
| 队列 | Queue | 任务的有名有序组合，生成时赋予随机短 id（保证唯一，删除后不刻意复用；非提交顺序号）。生命周期四态：未提交 / 已提交 / 执行中 / 已完成（**成功为唯一稳定终态**），**流转非单向**——已提交未开始的队列可整席移出待执行队列、回退为未提交；执行结束按结果分流：全部成员成功 → 记「成功」、停留已完成（不可回退或重提交）；存在任一 failed/skipped 成员 → 记「失败」（结束原因：失败中止 / 跳过跑完仍有失败 / 手动停止，并记录失败成员与各自归因——失败中止时即死在哪一个任务上、因何死掉）并**自动回退为未提交**，可编辑后重新提交；回退队列虽处未提交态，但**携带回退标记与回退次数**（连同失败成员与归因一并展示），与新建的未提交队列明确区分——避免被当成新鲜队列、未经修改就再次提交。成功判据只看当前成员构成：还存在任一 failed/skipped 成员即记失败，**只剩 succeeded 成员才记成功**；回退编辑中移除全部 failed/skipped 成员（只剩 succeeded）后自动标记为成功、就此终结。重新提交以**队列**为单位：按队列 id 取其当前成员执行，不与上次提交的内容或顺序绑定——成员与顺序均取派发当下的最新值（见下「输入哈希与重新提交」与「派发原则」）。成员数 2–10 **仅在创建时校验**；**创建后成员只减不增、至少保留 1 个**——移除至单成员后不可再移除，队列不因成员减空而除名（删除队列见「编辑与移除边界」）。可「保存」（仅存盘不执行，另择时间提交）或「直接提交」（存盘并进入执行），提交前必先保存。已提交队列的**未执行成员仍可重排、移除**（退回候选列表；不可改名、不可编辑内容），正在执行与已完成的成员为既定历史；**回退为未提交的失败队列，成员列表整体重新开放**——内容可编辑、可重排、可移除（含 succeeded/failed/skipped，见下「编辑与移除边界」）。删除队列仅可在队列列表页发起（唯一删除队列实体的入口）、需二次确认：未执行成员退回候选列表，已执行过（含 failed/skipped）的成员只留历史；执行中的队列不可删除，在待执行中的队列删除时其席位随之撤销。 |
| 待执行队列 | Pending queue | 提交后的执行缓冲，成员可为单任务或整条队列（各占一席）。尾部追加；**未在执行的成员可重排、可移除**（正在执行者除外；席位内单任务不可改名、不可编辑内容；队列席位内**未执行**成员可移除——执行中的队列可清至只剩正在执行的成员，未开始的队列至多移除至剩 1 个；**已执行成员不可移除**）——派发只认执行序列的并行窗口（见「派发原则」），窗口自序列头推进，被触及的席位位于待执行队列头部区、不可整席重排或移除（席位内规则不变）；实体执行结束即离席（单任务进历史；队列至全部成员结束时——含失败中止的收尾成员——成功进历史、失败回退为未提交，释放席位），已结束实体不滞留待执行队列，队尾永远是窗口未触及的等待席位（除非待执行队列只剩在跑任务）。整席移除：单任务退回候选列表、队列回退为未提交（成员不变，含失败回退后重新提交的队列）。「重新排队」视同新提交，占用容量、满员即拒。**容量=在途席位上限**（单任务与整条队列各计 1 席——N 成员队列亦只占一席；含执行中的席位，默认 3、可配置，下限 1 上限 10）：满员即拒绝新提交并提示，调小时的挤出语义见 §2.5。成员变化即存盘。 |
| 执行 | Execution | 一次实际运行，粒度=任务（无论单任务还是某队列成员）。实际交给 HQ 的始终是单个任务。 |
| 执行历史 | History | 所有已结束的执行，可归档、**不可删除**；归档为独立页面、独立存储，归档条目不再出现在历史页。failed/skipped 条目提供「重新排队」（原样重跑）与「退回候选」（编辑再提交）两个动作：「重新排队」直接进入待执行队列并占用在途席位（满员拒绝，与一般任务同待遇）；「退回候选」以 `run/<执行id>/` 内实际执行的输入副本新建候选（新 id，**携带来源标记**：成功退回 / 失败退回-附归因 / 未运行退回），skipped 等无执行目录者回落任务输入副本。 |
| 结果 | Result | 仅**正常结束**的执行解析后产生的结构化数据，进入结果分析管道。 |

执行状态机（任务粒度）：

```
staged（已入待执行队列）
  → running（正在执行）
      → succeeded（正常结束 → 进入结果解析管道）
      → failed（非正常结束，必须归因：手动停止 / 程序报错 / 外部中断；
                勾选「跳过失败任务」时失败者同样记 failed，队列继续）
  → skipped（所属队列整队停止时未获得运行机会，归因：前序任务失败 / 队列被手动停止）

终态 succeeded / failed / skipped
  → archived（从执行历史归档，仅加归档标记，条目移入归档列表）
```

队列失败语义（含并行窗口，2026-09-23 定稿）：队列中某任务出错 → 该任务记
failed（无论是否勾选「自动跳过失败任务」）。未勾选：队列停止推进——未启动
成员**即时**记 skipped（归因=前序任务失败），执行序列照常越过该队列、继续
为其后任务补位；**已在跑的其他成员不连带终止**，任其自然跑完、自身结局
照记（在跑投入不浪费；手动停止才是即时终止语义）。在跑成员全部结束时
队列执行即告结束，记**失败**（结束原因=失败中止，失败位置=出错的成员）
并自动回退为未提交——**回退不提前**：收尾期间队列保持执行中、席位不变、
不可编辑（「未提交可编辑」与「尚有成员在跑」不得并存）。勾选：跳过失败者
继续跑完，并行窗口照常取其未启动成员。两种情况队列均记**失败**并自动回退
为未提交（判据与分流见 §2.1），失败成员与各自归因记入队列记录，供排查——
不能只说队列停了。任务结束由执行序列自动补位，无「队列结束顺延下一成员」
的专门动作。

手动停止语义：手动停止队列 → 其**全部在跑成员**各记 failed（归因=手动
停止，即时终止——与失败中止的「任其跑完」相反，用户意图就是停），其余
未执行成员记 skipped（归因=队列被手动停止），队列随即结束并记失败
（结束原因=手动停止，失败位置=被停止的成员、并行时可不止一个）并自动
回退为未提交，不受「跳过失败任务」开关影响；执行序列照常为其后任务补位。
历史条目一律不可变，移除类操作不存在撕裂历史问题；总边界见下
「编辑与移除边界」。

编辑与移除边界（2026-09-22 定稿）：任务内容编辑只有两个入口——候选列表
（M2 分块编辑）与回退为未提交的失败队列（队列编辑框内点击成员进入同一套
分块编辑，分块结构与 M0 契约共用）。已提交/待执行中队列的**未执行**成员
不可改名、不可编辑内容，只可重排、移除（移除 → 退回候选列表）；正在执行
与已执行的成员为既定历史，**不可移除**——已执行成员只有在队列回退为未提交
后才能移除，且按结局分流：succeeded 成员移除 → 脱离该队列（历史条目与
文件保留，不生成新候选；要复用其输入走历史条目的「退回候选」）；failed/
skipped 成员移除 → **退回候选列表**（文件正确性未经验证：failed 以
`run/<执行id>/` 实际执行的输入副本、skipped 以任务输入副本新建候选，规则
同历史条目的「退回候选」，**携带来源标记**——失败退回附归因、未运行退回
标注从未执行，与新鲜导入的候选明确区分），供编辑后再利用。移除下限：
未提交（含回退）与已提交未开始的队列，至多移除至剩 1 个成员；执行中的
队列其未执行成员可全部移除、清至只剩正在执行的成员。队列实体不可因成员
减空而除名，删除队列实体的唯一入口是队列列表页（二次确认）。

输入哈希与重新提交（2026-09-22 定稿）：每个任务执行前计算输入文件哈希并
记入历史条目。失败队列回退编辑后重新提交时以**队列**为单位：按队列 id 取其
当前成员执行，不与上次提交的内容绑定——内容是否改过由哈希在派发该成员时
判定，提交动作本身不管；成员上次成功且当前输入哈希与该次成功记录一致 → 跳过执行、沿用
既有结果（不新增执行记录，成员状态保持 succeeded）；哈希已变或从未成功
（failed/skipped）→（重新）执行。

派发原则（仓库模型，2026-09-23 并行定稿）：待执行队列按席位顺序**展开为
扁平的执行序列**——单任务席位即其自身，队列席位展开为该队列当前的成员
序列，单任务与队列成员在序列中平权（与「执行粒度=任务」一致）。执行器
（搬运工）只认「执行序列的并行窗口」——自序列头**按序**取「并行执行数」
（运行级设置，默认 1=串行、上限 6，见 §2.5）个任务进入执行，**只有在真正
要派发下一个任务时，才去取该任务的信息**（输入哈希、id 去重均在该时点）；
某任务结束，序列**自动补位且保序**——下一任务的声明资源（Link0 之
`%NProcShared`/`%Mem` 及补齐值）大于空闲资源（worker 总资源 − 在跑任务
声明值之和）时，窗口停在该任务等待释放，**不越位取其后的小任务**，队头
阻塞是显式接受的代价（顺序公平优先，不设越位例外）。窗口之外的一切
（重排、移除、整席移除、队列内部成员与顺序）在真正执行前都可能被修改，
提交时的顺序不构成承诺，且不影响正在执行者。资源记账双账：窗口推进由
g16web 按声明值自算，同时将 `%NProcShared`→`cpus`、`%Mem`→`mem`（GB→MiB
换算）作为 HQ 资源请求随任务提交，交 HQ 调度器做第二道防线（防记账漂移
与外部提交者）；实耗监控走 psutil（§8.4），声明账与实耗账分层各司其职。
派发时按
**任务 id、队列 id** 去重兜底：去重针对 **id 复用**而非重复执行——id 一经
进入历史即被永久占用（含已删除实体），新候选/新队列的 id 生成必须对照
全库（含历史）查重、永不复用，防止历史条目归属歧义；同一存活任务的再次
派发（失败重跑、历史「重新排队」）不属 id 复用，同一任务产生多条历史条目、
共享归属任务 id 属设计内行为（见 §2.6 ③）。

### 2.4 文件治理与路径边界

工作区根目录（默认 `~/g16web/`，可用 `G16WEB_HOME` 覆盖——单根体系，已定稿；
此前 `~/scratch` 下的临时数据不迁移）统一管理全部文件。**SQLite 为元数据唯一事实
来源**（候选/任务/队列/待执行/历史），目录只存文件实体：

```text
g16web.db      SQLite：全部元数据与状态
inputs/        输入副本（候选与任务按各自 id 存放；导入即拷贝、与源文件彻底独立）
run/<执行id>/  执行工作区：输入、输出、日志、scratch（chk/rwf 等）
```

规则：

- 导入：任意路径（含 `/mnt/c/...`）只读取一次并拷贝入库，此后不再依赖源文件。
- 候选任务被「-」剔除 → 删除其输入副本与记录（**删除任务实体的唯一入口**）；
  被提交或被选入队列 → 转为任务（移动语义，移出候选列表）。
- 删除队列时：未执行成员退回候选列表；已执行过（含 failed/skipped）的成员
  不退回，经历史页「重新排队/退回候选」触达。单独移除队列成员、整席移除
  待执行成员同此——未执行者退回候选列表，绝不删除；回退队列中已执行成员的
  移除按结局分流（§2.1）：succeeded 脱离队列（历史条目与文件保留，不生成
  新候选），failed/skipped 退回候选列表（副本规则同历史「退回候选」）；历史
  「退回候选」以
  `run/<执行id>/` 内实际执行的输入副本新建候选（skipped 无执行目录，回落
  任务输入副本）。
- 写操作（编辑保存、执行产物）只发生在工作区内；工作区外的路径一律只读。
- M5 的 DSH 安全边界直接沿用本节：可读=工作区，可触发=契约内操作。

### 2.5 配置治理（设置面板，2026-09-22 定稿）

参数分两级：

- **启动级（不宜运行中更改）**：工作区根 `G16WEB_HOME`（默认 `~/g16web/`）、
  监听地址（默认 `127.0.0.1`——只绑回环是安全边界，见 §5）、
  派发引擎开关 `G16WEB_ENGINE`（默认开；`=0` 关闭进入 M0 演示模式，M1 起）、
  HQ 可执行定位 `G16WEB_HQ_BIN`（默认按 PATH 探测，回落仓库构建产物）——经环境变量覆盖
  （前缀 `G16WEB_`），设置面板只读展示。
- **运行级（除启动级外一律）**：监听端口（初始默认 8300，**保存后下次重启
  生效**——启动时从设置读取，无记录回落代码默认值）、在途席位上限（初始默认 3，下限 1、上限 10；单任务与整条队列各计
  1 席，N 成员队列亦只占一席；**调小即时生效并自待执行队尾挤出**——单任务
  退回候选列表、队列由已提交回退为未提交；挤出只作用于窗口未触及的等待席位，
  并行下在跑席位可能不止一个，对已开跑者一律不追溯——在途席位可临时超出
  新上限、随执行结束自然收敛（§2.1）；调大即时生效、空闲容量即可用。本参数为
  「即时生效且追溯」的显式特例，其余影响执行语义者按下方通则不追溯）、
  并行执行数（执行序列并行窗口的大小，初始默认 1=串行、下限 1、上限 6，
  经设置面板调大即开启并行；调大即时生效，调小对在跑任务不追溯、窗口按
  新值收敛，见 §2.1 派发原则）、
  chk/rwf 保留期（初始默认 7 天）、停滞告警阈值（初始默认 10 分钟无新优化步/
  SCF 迭代）、分页大小（初始默认 50）、SSE 心跳间隔（初始默认 15s）、Link0
  缺失补齐默认值、g16 执行环境（见下条）等——**由 WebUI 设置面板确定，不经
  环境变量**；写入 SQLite（元数据唯一事实来源），代码默认值集中在
  `web/src/config.py`。
- **g16 执行环境（2026-09-22 实测）**：发行目录 `~/g16`（`g16root=$HOME` 的
  `$g16root/g16` 布局），主程序 `~/g16/g16`、`formchk` 同目录；完整环境等价于
  source `~/g16/bsd/g16.profile`（设置 `GAUSS_EXEDIR`/`GAUSS_BSDDIR`/
  `G16BASIS`/`GAUSS_ARCHDIR`/`GAUSS_LEXEDIR` 及库与可执行搜索路径）。g16web
  派发时按此自洽构建子进程环境，并**每次执行强制 `GAUSS_SCRDIR=run/<执行id>/`**
  （不沿用全局 `~/scratch`，旧数据不迁移，见 §2.4）；环境改动仅影响其后新
  提交的任务。

生效规则：设置即时持久化、及时应用；**凡影响执行语义的参数，对正在执行与已在
待执行队列中的成员不追溯，仅对其后新提交（新进入待执行队列）的任务/队列生效**；
不影响执行语义的（如分页、心跳）即刻生效；端口保存后下次重启生效（面板保存
时提示需重启）。逐参数的生效边界在 M0 契约的设置
端点中标注；参数全集与逐项语义尚未列全（开放事项见 §7）。

### 2.6 属性清单与字段生命周期（M0 契约输入）

字段治理三层规则：

1. **字段集一次定死**：领域对象的全部字段在 M0 契约定稿时一次定义完毕；
   实现途中不得新增字段——那等于契约变更，须走文档 diff（§4）。
   SQLite 建表时列全部存在，无值字段为 NULL/默认值，必填与可空语义由契约标注。
2. **值按状态流转填充**：可变实体（候选/队列/执行中）随状态改值；执行记录
   到达终态即冻结，此后唯一允许的变更是 archived 归档标记——这是「历史
   不可变、不存在撕裂历史」在存储层的前提。
3. **跨里程碑整体扩展**：新字段（M3 的 Result 字段、M4 的任务链依赖等）随
   该里程碑的契约 diff 一次性扩展（Result 已在 M0 占位），不实现途中随手加。

字段生命周期表（「创建」= 该实体记录落库的时点）：

| 对象 | 属性 | 赋值时机 |
|---|---|---|
| Candidate（创建即完整，此后不变） | id；文件名；输入副本引用（`inputs/<id>`，id 派生）；来源标记（导入 / 未运行退回 / 失败退回 / 成功退回）；失败归因附注（仅失败退回） | 全部创建时；title 不落库、展示时实时解析（已定稿） |
| Task（除墙钟上限外零自有属性，纯关系） | 归属队列 id（直接提交者为空）；队列内顺序位置；墙钟上限 time_limit（默认 0=不限制，可按任务设置；派发时映射为 HQ time_limit，0 则不设） | 入队/重排时更新；墙钟上限入队/提交时设置（缺省 0）；id 跨形态延续——候选↔任务同 id（已定稿） |
| Queue | 队列 id（随机短 id）；队列名；成员有序列表（创建 2–10，此后只减不增、至少 1 个）；跳过失败任务开关 | 创建时 |
| Queue（续） | 状态（未提交/已提交/执行中/已完成）；回退标记；回退次数；最近失败记录（失败成员与各自归因、失败位置）；结束原因（成功 / 失败中止 / 跳过跑完仍有失败 / 手动停止） | 状态随流转更新；回退标记/次数在失败回退时置位/+1；最近失败记录在执行结束记失败时写入、队列转为成功终态时清除；结束原因在最近一次执行结束时写入 |
| PendingQueue | 席位有序列表（单任务/队列各占一席） | 追加/移除/重排时更新；容量为运行级设置，非持久属性 |
| Execution / HistoryEntry | 执行 id（`run/<执行id>/` 由其派生）；归属任务 id；归属队列 id（可空）；提交时间；输入哈希（执行前计算）；资源配置之 Link0 声明与补齐值；HQ job id 引用（提交 HQ 后回填，重启对账用） | 派发创建时 |
| Execution（续） | 启动时间；运行时实采资源配置 | running 时补 |
| HistoryEntry（终态补齐后冻结） | 结束状态（succeeded/failed/skipped）；归因（手动停止/程序报错/外部中断/前序失败/队列被手动停止）；结束时间（耗时为派生）；chk/rwf 保全快照标记与位置；执行监控摘要（CPU/内存峰值、停滞告警次数与时长，**仅 succeeded 条目**） | 终态补齐后冻结 |
| HistoryEntry（冻结后） | archived 归档标记（唯一可变字段）；Result 引用（仅 succeeded，M3 占位） | 归档时置位；M3 起写入 |

三项已定稿（2026-09-22，随 M0 契约落为字段与校验）：

- ① **title 实时解析**、不落库（M1 列表展示时现场解析输入文件）；
- ② **执行监控摘要落历史**：CPU/内存峰值与停滞告警（次数/时长）记入
  历史条目，**只取运行成功（succeeded）的数据**——failed/skipped 条目不留
  摘要（运行中的实时监控查看不受影响）；
- ③ **id 跨形态延续**：候选↔任务始终同 id（移动语义）；历史「退回候选」
  仍新建 id（属复制、不是移动）。id 唯一性约束在**生成侧**：id 一经进入
  历史即被永久占用（含已删除实体），新候选/新队列的 id 生成必须对照全库
  （含历史）查重、永不复用，防止历史条目归属歧义；**同一存活任务的再次
  执行不受此限**——失败重跑、历史「重新排队」沿用原任务 id，同一任务可
  产生多条历史条目（共享归属任务 id）。

### 2.7 Gaussian 输入文件结构与空行规则（2026-09-23 据 G16 手册核查）

原型踩坑记录转化的设计输入，依据 G16 手册
[gaussian.com/input](https://gaussian.com/input/)（Syntax、Section Ordering）与
[gaussian.com/zmat](https://gaussian.com/zmat/)。输入为 ASCII 文本、自由格式、
大小写不敏感，按**节**组织；空行是绝大多数节的终止符：

| 节 | 终止空行 | 要点 |
|---|---|---|
| Link 0 命令（`%` 行） | **不需要** | `%Chk`/`%RWF`/`%NProcShared`/`%Mem` 等，其后 route 直接跟随（手册示例有无空行均出现过，非必需） |
| Route 节（`#` 行） | 必须 | 计算类型、模型化学与选项；`!` 注释行可出现在输入任意处 |
| Title 节 | 必须 | **至多 5 行**；避免 `@ # ! – _ \` 与控制字符；程序不解释、仅作输出标识（§2.6 ① 的 title 即此节） |
| 分子说明节 | 必须 | 首行 = 电荷 多重度，其后为笛卡尔坐标或 Z-matrix；`Geom=AllCheck` 时本节与 title 可整体省略，`Geom=Checkpoint` 时仅保留电荷多重度行 |
| 附加输入节（可选） | 绝大多数必须 | 由 route 关键字触发（Opt=ModRedundant、Gen、Guess=Alter、SCRF=Read 等）；是否需要终止空行以手册 Section Ordering 表逐节为准，个别例外为 no（Guess=LowSymm、GVB、Pop=NBORead、Output=Pickett/WFN 等） |

Z-matrix 变量区：原子定义行连续排列，其后以**空行**分隔 `Variables:` 变量区，
再以**空行**分隔可选的 `Constants:` 常数区（部分优化的固定项）。

多步任务：`--Link1--` 行分隔各 job 步，**其前必须有一个空行**（上一节的
终止空行即充当之）。

对分块模型的直接约束（M0 契约与 M2 编辑共用，§3）：

- 分块保存重组时，除 Link 0 外**每节末尾恰好一个空行**（含文件末节与文件
  末尾）；Link 0 之后不加空行。
- 坐标块不可编辑（M2），但保存重组不得丢失或增删 `Variables:`/`Constants:`
  区之间的空行分隔。
- 多步任务（含 `--Link1--`）的文件是否允许导入，须在 M0 契约明确；若不支持，
  导入校验须拒绝并提示。

### M1 · 队列与执行（核心闭环）
自持队列执行引擎 + 监控 + 候选任务入口（导入、候选列表、只读预览），入口一次
成型。批量导入 `.gjf` / `.com`：单文件或多选（多选按文件名自然序排列——不区分
大小写，字母优先，即 A–Z 先于 0–9）；另有「导入文件夹」——选择文件夹一键导入
其中所有受支持输入文件（默认仅生成候选；以文件夹名为队列名导入见 M2）；
导入即拷贝入库、与源文件彻底独立（§2.4）。

- 候选任务列表（页面左半部分，显示 id、文件名、title（实时解析）、来源标记——失败退回
  附归因、与新鲜导入显著区分，见 §2.1）：点击任务行 → 右侧只读
  预览关键信息——分块显示 title、Link0、路由层、价态/自旋多重度，统计原子数
  （不含坐标这类大块文本）；本里程碑内预览仅只读（编辑见 M2）；「-」剔除候选，
  存储规则见 §2.4。
- 行内提交（长期快捷通道；单任务快速提交，跳过队列组建，但同样经待执行队列
  排队、不插队；在途席位满员（默认 3）时拒绝提交并提示）：候选任务行内
  「提交」→ 确认框含纯文本只读预览完整输入（含坐标，限高加滚动条）；提交前
  检查 Link0 资源分配（至少含 `%NProcShared`/`%Mem`），缺失项在确认框显示黄色
  警告并告知将按默认值填充。
- 待执行队列页：成员（单任务/队列，各占一席）尾部追加、在途席位上限 3（满员拒绝
  新提交与「重新排队」）；未在执行的成员可重排、可移除（正在执行者除外，
  派发只认执行序列的并行窗口，见 §2.1）——单任务整席移除退回候选列表（不可改名、
  不可编辑内容），队列整席移除回退为未提交，队列席位内未执行成员可移除
  （执行中的队列可清至只剩正在执行的成员，未开始的队列至多剩 1 个；已执行
  成员不可移除，见 §2.1）；容量调小的挤出语义见 §2.5。
- 派发：按执行序列的并行窗口派发（§2.1 派发原则；并行数默认 1=串行起步、
  调大即并行，上限 6）——任务结束自动补位，下一任务声明资源不足则窗口停等。
  资源记账双账：Link0（`%NProcShared`/`%Mem`）缺失项按默认值补齐（默认值集中
  在 `web/src/config.py`、经设置面板管理，见 §2.5），补齐值记入历史的资源配置，
  并映射为 HQ 资源请求（`cpus`/`mem`，GB→MiB 换算）随任务提交；窗口推进由
  g16web 按声明值自算。g16 子进程环境按 §2.5 实测配置自洽构建，每次执行强制
  `GAUSS_SCRDIR=run/<执行id>/`；每个任务执行前计算输入文件哈希记入历史
  条目（供失败队列重新提交时的跳过判定，见 §2.1）。
- 执行中页：**在跑任务列表**（并行数>1 时多任务同屏，按执行 id 键控），每任务
  行含关键信息、提交时间、启动时间、已运行时间、CPU/内存占用监控（Python 侧
  psutil 采 g16 进程树，见 §8.4）；停滞检测**只提示不自动终止**——增量解析发现超过
  阈值（可配置）无新优化步/SCF 迭代即告警，是否终止由用户决定；默认不设 HQ
  time_limit 墙钟上限（任务属性可配、默认 0=不限制，见 §2.6），卡死处置一律走
  「提示 → 用户决定」；
  手动强行停止需二次确认，停止后可移除。
- 失败语义与归因：手动停止 / 程序报错 / 外部中断（含 WSL2 重启）逐类归因记入
  历史；队列失败与手动停止的整队语义按 §2.1 处理（未勾选跳过或被手动停止时，
  未运行成员记 skipped）；failed/skipped 条目提供「重新排队」（原样重跑，经
  待执行队列、占用在途席位，满员拒绝）与「退回候选」（以 `run/<执行id>/`
  输入副本新建候选再编辑提交）两个动作。
- 执行历史：结束状态、提交时间、起止时间、耗时、输入文件哈希（执行前计算，
  见 §2.1）、资源配置（线程/内存，取自 Link0 与运行时）、执行监控摘要
  （CPU/内存峰值与停滞告警次数/时长，仅 succeeded 条目，见 §2.6）、归属
  队列；可查看
  输入（纯文本形式）、纯文本预览并导出输出文件；可归档不可删除。
- SSE 推送运行中进度（自写增量解析：优化步/SCF），事件契约按 M0 定稿执行；
  SQLite 持久化，g16web 重启后候选/队列/待执行/历史全部恢复，并与 HQ 实态对账
  ——执行记录登记对应的 HQ job id，按此映射识别重跑者（注意 §8.6 的 journal
  恢复语义）。
- HQ 侧既定改造（§8.8）：server 进程内新增 HTTP/JSON 层（绑 `127.0.0.1`）与
  SSE 事件桥接（桥接 EventStreamer），复用 HQ 功能模块供执行集成与实时推送。
- 执行成功后自动 formchk 生成 `.fchk` 留在 `run/<执行id>/`（供 M3 可视化）。
  文件清理边界（定稿）：**自动清理只作用于 `.chk`/`.rwf` 与 scratch，永不触碰
  `.out`/`.log` 与输入文件**；正常结束的 chk/rwf 按保留期清理（默认 7 天、可配置），
  历史页提供清理入口；**非正常终止的 chk/rwf 不受保留期约束**（续跑资产，仅用户
  手动清理），终止时立即保全快照（改名移入保护子目录并记入历史条目）。写半截的
  `.out` 永久保留、历史页可查看（纯文本预览对截断容错，`errors="replace"`）；
  输入与输出/日志归档保留并标记归因。

**验收**：批量导入 3 份输入（含同一文件重复导入，验证 id 唯一）→ 候选列表显示
id/文件名/title → 点击行只读预览关键信息 → 行内提交（确认框含坐标；缺
`%NProcShared`/`%Mem` 时显示黄色警告）→ 实时看到优化步/SCF → 强制停止

- 与 Gaussian 零关系：全仓检索 gaussian/g16/quantum 等关键词零命中，g16 只是
  普通子进程任务。

### 8.2 传输、协议与发现

- 客户端↔server **仅 TCP**：长度分帧 + bincode(fixint) + orion AEAD 挑战-应答，
  无密钥时明文并告警（`tako/src/internal/transfer/auth.rs`）。
- UDS 只用于 worker 与其本地任务进程间的通知通道（`hq-lc-*` socket），
  client↔server 不支持 UDS。
- 服务发现：`~/.hq-server/{编号目录}/access.json`（0o400，含地址与密钥）+
  `hq-current` 软链（`common/serverdir.rs`）；server 端口默认随机分配。
- 消息协议：客户端→server 18 类请求、server→客户端 19 类响应
  （`transfer/messages.rs`），tako 层 worker 消息 8+6 类——规模可控。
- `--output-mode json`（env `HQ_OUTPUT_MODE`，全局生效）：Output trait 的
  20 个打印方法中 18 个有 JSON 实现；**两处直接报错、拒绝 JSON 模式：
  `hq job cat`（任务输出）与 `hq alloc log`（分配日志）**（`client/output/json.rs`
  的 `print_job_output` / `print_allocation_output`）——读任务输出与分配日志
  不能走 CLI JSON。

### 8.3 调度与资源模型（单机用不到的部分）

- 布局求解：highs / microlp / coin_cbc 三后端经 Cargo feature 互斥切换
  （默认 highs，`tako/src/internal/solver/`），每轮对「任务批次 × worker ×
  资源变体」建 0/1 变量求布局；无解不报错，任务留队等下一轮。
- 资源请求：`cpus` / `gpus:nvidia|amd` / `mem` + 任意自定义资源；放置策略
  Compact/Tight/Scatter；单任务可带多个资源变体；NUMA 以 CPU groups 表达。
- worker 资源 = 启动探测 + `--resource` 声明。
- 以上灵活性单机场景全部用不上；feature 隔离意味着删 LP 后端切口干净（§8.8）。

### 8.4 硬件探测与运行时监控（M1 关键）

- 探测：`crates/hyperqueue/src/worker/hwdetect.rs`（336 行）——NUMA 读 `/sys/devices/system/node`、
  超线程剪枝 `thread_siblings_list`、内存走 sysinfo；GPU 计数先看
  `CUDA_VISIBLE_DEVICES`/`ROCR_VISIBLE_DEVICES`，否则数 `/proc/driver/nvidia/gpus`。
- 运行期采样（`tako/src/internal/worker/hwmonitor/`）：sysinfo 采 CPU/内存/网络，
  `nvidia-smi --query-gpu`（AMD 用 rocm-smi）采 GPU，产 `WorkerOverview`。
- **能力边界（M1 直接结论）**：
  - WorkerOverview 是 **worker 整机**指标 + 任务**资源分配**（哪些核/GPU 分给
    哪个任务），**不是任务进程级的实时 CPU/内存占用**；
  - 且默认**关闭**（`hq dashboard` 或事件流 `enable_worker_overviews` 打开时
    才以 2s 间隔采集）；
  - ⇒ M1 的「CPU/内存占用监控」**优先 Python 侧 psutil 采 g16 进程树**（后端与
    worker 同机零 HQ 改动：按 `run/<执行id>/` 的 cwd 匹配定位进程，CPU 取采样
    差值、内存汇总树内 RSS，Linux 上 g16 会依次派生 `l*.exe` 段进程故需树汇总；
    GPU 后续经 `nvidia-smi` 同路径采），确实不敷需求再改 `crates/` 源码。HQ 不向
    客户端暴露任务子进程 PID（tako worker 消息无此字段），不走「向 HQ 要 PID」
    路线（2026-09-22 定稿，ADR 0001 首个改造场景相应让位于 §8.8 HTTP/SSE 层）。
- WSL2 受限功能集下 nvidia-smi 字段可用性仍需目标机实测。

### 8.5 任务输出与日志（M1 增量解析的约束）

- 默认 stdout/stderr = worker 本地文件 `%{CWD}/job-%{JOB_ID}/%{TASK_ID}.stdout`
  （stderr 同名 `.stderr`）；`--stream=DIR` 则以管道采集为 `.hqs` 离线流文件
  （`hq output-log` 系列读取）。
- **任务输出没有网络实时流**：`hq job cat` 由客户端**本地读文件**，要求客户端
  与 worker 同文件系统；JSON 模式不支持（§8.2）。
- ⇒ 对策：g16web 后端与 worker 同在 WSL2，把 g16 任务的 cwd 指到
  `run/<执行id>/`，自写增量解析直接读该目录下输出文件即可——不需要 `--stream`，
  也不动传输层，这是单机场景的最短路径。

### 8.6 事件、Journal 与恢复（SSE 推送与重启对账的约束）

- 事件总线：`EventStreamer::register_listener(filter, UnboundedSender<Event>)`
  进程内订阅，按 JOB/TASK/WORKER/ALLOCATION/NOTIFY 过滤（`server/event/streamer.rs`）；
  外部消费者（dashboard、`hq job wait/progress`、`submit --wait`）一律经
  `StreamEvents` RPC。⇒ g16web 的 SSE 桥接 = server 进程内加一个 listener 转
  JSON 推流，机制现成、无需重写。
- Journal：bincode 追加流（magic `hqjl0002`），独立写线程周期 flush、容忍半写；
  **`--journal` 是可选参数，不传即无持久化**；prune 重写只留 live 事件。
  g16web 托管 HQ server 时必须显式传 journal 路径。
- **恢复语义（对账关键）**：带 journal 重启时终态任务恢复原
  状态，而 Waiting/Running 任务**重新提交执行**（`server/restore.rs` restore_job）
  ——HQ 不保留「中断」状态而是静默重跑。⇒ g16web 对账若简单「以 HQ 为准」，
  会把外部中断误判为重新执行；须按执行记录登记的 HQ job id 映射识别重跑者、
  对照本地中断记录再归因。
  处置已定稿（原开放事项 3）：**采纳重跑**，但 g16web 重新物化输入时检测「存在
  保全 chk 且任务可续跑」，默认重定向到新执行目录——g16 启动会重写 `%CHK` 文件，
  不重定向就会抹掉续跑资产；「从断点续跑」为历史条目上的显式动作（本体随 M4
  §7.1 物化机制实施），M1 落地保全（见 M1 文件清理边界条目）与重定向。
- 失败重试：worker 心跳默认 8s、2× 超时判失联；失联后其运行中任务按 crash_limit
  （默认 MaxCrashes(5)）**自动重新入队**。⇒ 归因时注意任务可能被 HQ 自动重跑过，
  仅最终失败入历史。

### 8.7 任务状态机（失败归因的依据）

- HQ 任务 6 态：`Waiting / Running / Finished / Failed / Canceled / Aborted`
  （`server/job.rs:28`）；job 级状态由任务计数推导（`client/status.rs`）。
- `time_limit` 由 worker 侧强制执行（`tako/.../worker/reactor.rs:249-253`）：
  超时杀进程，报 `Failed`（"Time limit reached"）。定稿：**默认不设 time_limit**
  ——墙钟上限对时长跨度极大的化学任务过钝；计算停滞由应用层检测（增量解析，
  见 M1 执行中页），**只提示不自动终止**，是否杀死由用户决定。
- M1 三类归因的映射依据：手动停止 ← g16web 主动取消（HQ 记 `Canceled`）；
  程序报错 ← `Failed` 且非超时、非失联；外部中断 ← worker 失联重排与 journal
  恢复场景（§8.6）。
- 进程连带语义（定稿，保持 HQ 默认机制、不配 FinishRunning）：任务子进程设
  `PR_SET_PDEATHSIG=SIGTERM`（`tako/src/launcher.rs:189`）——worker 死则 g16 被
  内核终止；HQ server 死则 worker 按默认 `--on-server-lost=Stop`
  （`client/commands/worker.rs:280`）取消在跑任务并退出
  （`tako/.../worker/rpc.rs:296-310`），进而连带终止 g16；**g16web 自身死亡不影响
  在跑计算**（HQ server/worker/g16 均为独立 OS 进程），重启后走 SQLite+journal
  对账。单机场景下「连带终止 + journal 重跑 + chk 续跑」优于放任孤儿进程。

### 8.8 改造方向备忘

总方向：复用 HQ 的功能模块、弃用其 TUI，以本工作台 WebUI 作为综合管理面板。
改造动手前须在本文件补设计与验收标准。

**既定工作**（纳入里程碑）：

- **统一本地 HTTP/JSON API 与 SSE 桥接**：axum 绑 `127.0.0.1`，REST + SSE
  （桥接 EventStreamer）；M0 完成契约覆盖，M1 在 server 侧实施 HTTP 层与事件
  桥接；TCP/bincode/orion/auth/`~/.hq-server` 发现在单机回环下可整体退场。

**设计定稿与验收判据**（2026-09-23 A1 定稿，全文见
[m1-plan.md](../plans/m1-plan.md) §2.1，此处为摘要）：

- **职责边界**：g16web FastAPI 层面向浏览器（M0 契约 33 端点 + 12 类事件，
  领域语义）；HQ server 内 HTTP/SSE 层唯一预期消费者是 g16web 后端（执行
  事实：job 状态/资源分配/worker 存活）。两层均无认证（回环即边界），HQ 层
  一律绑 `127.0.0.1`、端口由 g16web 经 `--http-port` 传入，**默认不开**
  （不传参数 HQ 行为零变化）。
- **HTTP 端点集**（7 个）：`GET /info`、`POST /jobs`（program/cwd/env/
  stdout/stderr/resources{cpus,mem_mib,time_limit_s}）、`GET /jobs/{id}`、
  `GET /jobs?ids=…`（批量状态）、`POST /jobs/{id}/cancel`、`GET /workers`、
  `GET /events`（SSE）。复用 CLI 内部命令实现保证双路一致。
- **事件桥接**（2026-09-23 实地核查 `server/event/payload.rs` 定稿）：
  EventStreamer `register_listener(EventFilter::all_events())` 进程内订阅，
  listener 断连自动清理（发送失败即移除）；axum SSE 帧格式
  `event: <变体名 snake_case>` + `data: 单行 JSON`（`{time, 字段…}`）。
  事件全集 22 变体：M1 订阅 job/task/worker/server 四域（Submit、JobOpen/
  Close/Completed/Idle/Cancel、TaskStarted/Finished/Failed、TasksCanceled/
  Aborted 批量、TaskNotify、WorkerConnected/Lost、ServerStart/Stop）；
  `Submit.serialized_desc` 为 bincode 字节不透传（g16web 自持提交内容，帧
  仅含 job_id/closed_job）；WorkerOverviewReceived 默认关闭不订阅；
  Allocation* 五变体单机本地模式不产生。薄桥接不缓存不重放，断线缺口由
  g16web REST 对账补齐（§8.6）。
- **验收判据**（五条，H4 逐条验证、D1 复核）：① `--http-port` 启动后 curl
  完成「提交→查询→取消」，JSON 与 CLI `--output-mode json` 等价；②
  `GET /events` 收到单 job 全生命周期事件，帧为合法 SSE 单行 JSON；③
  g16web 经 HttpGateway 完成「提交→事件接收→终态落历史」集成闭环；④
  不传开关时 HQ 现有行为与测试零变化；⑤ `cargo test` 全绿。

**远期方向**（需求落地时按 §2.3 取舍表重新评估）：

- **单一 daemon**：执行器并入 server 进程（pyhq LocalCluster 已验证同进程可行），
  删 worker 心跳/失联检测（须接手其任务恢复语义，见 §8.6），任务卡死兜底交给
  time_limit。
- **槽位化调度**：cpus/mem 记账 + GPU 独占槽替代 LP 布局；三求解器经 feature
  隔离、切口干净。
- **删 AutoAlloc**（`server/autoalloc/` 恰 4,500 行）、多节点、NUMA/资源变体等
  单机无关部件。
